# L4 × gpt-oss-20b (mxfp4): batching and pbatch vs vLLM 0.32.0

Run `20261103-2218-l4-x1-gpt-oss-20b-batching` on one NVIDIA L4 (24 GB, sm_89, 72 W power cap)
on RunPod.

* Fix branch: `r2g/20261103-2218-l4-x1-gpt-oss-20b-batching`, one commit `fa52aea7` on upstream
  `59935820d`.
* Evidence branch: `r2g-evidence/20261103-2218-l4-x1-gpt-oss-20b-batching`.

Every number below comes from a JSON under `results/`, and every table is regenerated by a script in
`scripts/` (§14).

## 1. Summary

**pbatch: already green on current main, and the site's pie value does not reproduce.**

* Best pf-N on this pod, 3 rounds: pie **7,684** (7,674–7,694) against vLLM 0.32.0's **6,580**
  (6,570–6,590), so **+16.8%**.
* The site's pie cell, 4,666 at pf8 for commit 8fb7e90e6 (TTFT 1,045 ms), does not reproduce. That
  same commit, built and run here, gives pf8 7,325 (TTFT 661 ms) and pf64 7,638.
* vLLM's site value (6,425 at pf64) does reproduce (6,563 here at pf64).
* Since the site measured, #1350 (the L4's 65% working set) raised pf256 from 4,904 to 7,676.

**Batching: level on main, within 2%.**

* The site's metric is each engine's best point of the c4–c1024 sweep. Here, 3 rounds: pie
  **1,752** (1,746–1,761), vLLM **1,785** (1,778–1,791), so **−1.8%**. That is inside the ±2% band,
  though pie sits just under vLLM in every round.
* The site's −28.1% does not transfer:
  * The site's vLLM row (2,193) is 23% above what vLLM does on this card at its harness defaults.
    pie's other site rows (raw, and batching at 8fb7e90e6) match this card within about 10% (§12.1).
  * pie gained after the measurement. #1350 alone takes 8fb7e90e6 from c512 1,436 to 1,714 and from
    c256 1,504 to 1,939 on this pod (single runs).
  * #1368's admission cap then costs c256 13% (1,987 → 1,729) and gains c512 2.5–5% (1,700 →
    1,743–1,784, depending on the session), which is why main peaks at c512.
* That cap is the remaining batching mechanism (§11): without it pie's c256 is 1,987, 11% over
  vLLM's best. It is engine-wide.
* No L4 profile setting I tried recovers c256 cleanly.
  * `seated_first = false`: c256 1,991, c512 1,574.
  * working set 55%: c256 1,744, c512 1,664.
  * `seat_to_end`: c256 1,743, c512 1,695.
  * graph bodies at 512 MiB: c256 1,803 and c512 1,752, single runs, but it arms 1 of the load's
    compositions and walks every shape eagerly, as upstream found on the RTX 4090 (#1417).
  (`results/knobs2`)

**The fix: one profile line closes a red stretch of the batching curve.**

* Before it, at c8 and c16 pie trailed vLLM by 13% and 32%.
* Cause:
  * gpt-oss-20b's c8 and c16 decodes route 32 and 64 routes over its 32 experts.
  * The L4 file's `moe.mxfp4_mma_per_from = 4` kept those selects off the register-dequant kernels.
  * Being under the grouping threshold, they ran the by-route MXFP4 select. That select streams an
    expert's codes once for every route: 40 ms of a c16 step whose ITL is 50 ms.
* With `= 0`, they take the 512-code run kernel, which pie already decodes c25–c128 with: 22.5 ms.
* 3 rounds over the whole curve:
  * **c16:** 299 → **500** tok/s (vLLM 442);
  * **c8:** 239 → **276** (vLLM 276);
  * every other point within ±1.2%, apart from two that are not the line's doing:
    * c4 +3.7%: its 16 routes stay under `mxfp4_mma_from`, so its kernel does not change.
    * pf8 −2.3%: pf8 is bimodal on this card (§7), and its prefill selects keep their kernel.
* Cost: c17–c24 move to the run kernel off the grouped wmma one. On the rebased pair, c24 loses
  2.2% (2 rounds, ranges apart) and c20 gains 1.7% (within spread).
* After the rebase, 2 rounds: c16 297 → 485, c8 241 → 280.
* The shipped commit `fa52aea7` differs from `6f038ac7` only in the comment's numbers. Its engine
  (`8b7e6b9b…`) gives c16 301 → 511, c8 243 → 284, c4 175 → 176 and raw 61.0 → 61.0 (§7).
* Cross-model:
  * gptoss-20b-mini: c8 +12%.
  * a 32-expert MiMo-V2.6-Flash miniature: c8 +37%, c4 +7%.
  * Nothing else moves outside the spread.
* Greedy tokens:
  * identical between base and fix for raw and pbatch on every model, in every round with dumped ids;
  * MiMo: identical at every shape, apart from c16 in one round, matching its base-vs-base noise;
  * at concurrency, pie's outputs vary run to run on one engine. At c8 and c16, where every decode
    step changes kernel, base and fix diverge more than that, as different accumulation orders do
    (§8).

## 2. How the site computes each metric

The GPU harness (pie-project/benchmarks) can't be read with this token: `gh repo clone` returns
"Could not resolve to a Repository". I reconstructed what it reports from three sources:

* **`scripts/bench/common.py:211-255` (`summarize`):** `output_tok_per_s = Σ output tokens / wall`
  (:242), with TTFT and latency percentiles over requests.
* **anton-mel/stats, `src/pie_evals/node/engines/base.py:100-150` (`perf_from_common_json`):** this is
  the Mac harness, and it drives the same `common.py` client.
  * `prefill_tok_s` = median over requests of `prompt_tokens / ttft`;
  * `decode_tok_s` = median over requests of `(n-1)/(latency-ttft)`.
* **The site's own rows:** `data/db.js`, snapshot `l4-full`, db updated 2026-11-03T22:01Z. They are
  checked for internal consistency by `scripts/site_rows.py`, output in `results/site_rows.txt`:

| row | prefill_tok_s / output_tok_s | output_tok_s × wall (wall ≈ TTFT p99) | reading |
|---|---|---|---|
| pie pbatch | 4666.45 / 7.66 = **609.2** tokens a request | 7.66 × 1.057 s = **8.1** requests | **pf8** |
| vLLM pbatch | 6424.65 / 10.58 = **607.2** | 10.58 × 6.043 s = **63.9** | **pf64** |
| SGLang pbatch | 558.40 / 0.92 = **607.0** | 0.92 × 34.29 s = **31.5** | **pf32** |

**pbatch.** Three things follow for `prefill_batch`:

* The site's `prefill_tok_s` is `Σ prompt tokens / wall`. The per-request median of `prompt/ttft`
  would be 609 / 1.045 s = 583 tok/s, not 4,666.
* The prompt is about 609 chat-rendered tokens: 512 plus gpt-oss's harmony preamble.
* **Each engine's cell is its own best pf-N:** pf8 for pie, pf64 for vLLM, pf32 for SGLang.

**Batching (`throughput`).**

* **pie:** 1,576.34 tok/s at a latency p50 of 40.1 s means each request holds a seat for about 41.6 s.
  1,576 × 41.6 / 128 ≈ 512 requests in flight, so the cell is **c512** (1,024 requests, wall ≈ 83 s).
* **vLLM:** 2,192.91 tok/s with a latency p99 of 119.5 s. vLLM's client submits every request at t=0
  (`scripts/bench/vllm_bench.py:538`), so its wall ≈ p99 latency, and 2,192.91 × 119.5 / 128 =
  **2,047 requests**: c1024 (2 × 1,024).
* Again, each engine's cell is its best point.

The two engines' latencies are not comparable:

* pie's client holds `--concurrency` requests open itself (`pie_bench.py:1100-1110`), so a request's
  clock starts when it gets a seat.
* vLLM's requests queue inside the engine (`max_num_seqs = concurrency`, `vllm_bench.py:373-376`), and
  its TTFT includes that queue.

The brief's "pie has better latency and ITL" comes from this difference, not from the engines.
pie's `raw` cell: 4,680.97 tok/s × 128.93 ms = 603.5 tokens, i.e. `prompt_tokens/ttft` per request.

**Setup here.**

* **Prompts:** built with `scripts/make_prompts.py` to exactly 225 chat-rendered tokens (batching) and
  609 (pbatch, raw), using the HF tokenizer.
* **Same tokens on both engines:** pie runs `--pretokenized-prompts`, so both engines prefill identical
  token ids. pie's own harmony rendering of the same text is 545 tokens (§12.4).
* **Shapes:**
  * batching: `tput --num-requests 2N --concurrency N --max-tokens 128`;
  * pbatch: `tput --num-requests N --concurrency N --max-tokens 1`;
  * raw: 8 requests one at a time, 256 out. vLLM's raw uses its streaming client at concurrency 1,
    since its latency mode stamps no TTFT.
* **Common flags** (harness defaults, both engines): `--warmup 2`, `--gpu-mem-util 0.90`,
  `--max-model-len 2048`.
* **Wrappers:** `scripts/bench.sh` and `scripts/sweep.sh`. Each run also samples SM clock and power
  once a second (`<label>.clk`; round 1 of `results/base` predates the sampler).

**#1350, the L4's 65% working set** (merged 2026-11-02 19:24 PST, after the site measured 8fb7e90e6).

* At 50%, gpt-oss-20b's 8192-row fires were served at 1,024 rows and pf256 at 128 lanes
  (`old/pie-old-8fb7e90e6-pf256-r1.log`: "max_forward_tokens 1024 and max_forward_requests 256 are
  served at 1024 and 128").
* At 65%, pf256 keeps 4,871-row fires: **+57% pf256, +29% c256, +19% c512.**
* This is the change that closed most of the gap. The site has not measured pie on L4 since it landed.

**#1368, the admission cap** (`crates/runtime/src/bootstrap.rs:318-341`).

* A seated-first pool admits at most `5 × total_pages × page_size / max_context` sequences (:327).
* At c512 the pool has 6,528 pages, so the cap is 255. From `diag/pie-c512-base-info.log`: "admission:
  capped at five sequences a sequence at the declared context holds in the kv pool requested=512
  seated=255". c512 gains 2.5–5%, depending on which session's main runs it is set against.
* At c256 the lanes (≤ 256) leave room for 8,192-row fires, the pool shrinks to 5,504 pages, and the
  cap is 215.
* The harness offers 512 requests of identical length, so they run in lockstep waves of
  215 + 215 + 82. The last wave decodes at a third of the width: on average 143 active lanes against
  194 (200.5 and 187.0) before #1368 (`wave avg active pipelines` in `results/attr`), and **c256 loses
  13%** (1,987 → 1,729).
* Turning `seated_first` off removes the cap: c256 1,991, but c512 falls to 1,574 because 512
  admitted lanes thrash the pool.

## 5. Attribution

**c512 (the batching cells' point).** nsys graph-level trace, 15.2 s of the measured window
(`results/prof/prof-c512-base-graph.graphs.txt`, `.gaps.txt`):

* The device is busy 15,016 of 15,208 ms (98.7%). Host-side gaps total 192 ms, one of which is 154 ms.
  pie is device-bound at c512, and host launch is not a factor.
* Decode steps (graph 47, about 254 lanes) take 72 ms: 96 runs, 6,912 ms.
* Prompt and mixed fires (graphs 116, 1, 20 and 35) take 42–190 ms each: 7,770 ms.
* So the window splits about 52% decode, 46% prefill or mixed, and 1.3% idle.

vLLM's ITL p50 at c512 is 121 ms, against pie's 84 ms. vLLM's steps carry chunked prefill (2,048
tokens) and about 220–262 running sequences, while pie's carry about 254. Both engines move the same
work through pools of the same size:

* pie: 6,528 pages × 16 = 104k full-attention tokens, capped at 255 seats;
* vLLM: 98.3k tokens, about 262 sequences of 353.

They finish 2.3% apart (c512: pie 1,744, vLLM 1,785). That is about the spread of either engine's
own rounds, so there is no per-component difference here big enough to attribute.

**c16 (the fix).** nsys node trace, about 1.1 s of decode (`results/prof/prof-c16-*.kernels.txt`):

| per decode step (≈20 steps in the window) | base | fix | vLLM |
|---|---|---|---|
| MXFP4 selects (48 a step) | `moe_matmul_select_mxfp4` 0.84 ms × 48 = 40.3 ms | `moe_select_mxfp4_mma_run` 0.47 ms × 48 = 22.5 ms | Marlin `fused_marlin_moe` |
| step (ITL p50, 3 rounds of §3) | 50.7 ms (52.4, 49.1, 50.6) | 29.8 ms (29.2, 29.0, 31.2) | 31.0 ms (30.0, 31.8, 31.4) |

The selects' delta (−17.8 ms a step in the traced window) is 85% of the ITL delta (−20.9 ms).

pie code (effective L4 values: `kernels-cuda/src/tuning.rs` defaults, then `profiles/sm89.toml`, then
`sm89/nvidia-l4.toml`):

* `mxfp4_mma_spans` (`crates/kernels-cuda/src/linear/moe/select_fp4.rs:27-32`) admits a routed MXFP4
  select to the register-dequant kernels only when
  `mxfp4_mma_from (28) <= routes <= mxfp4_mma_until` **and**
  `ceil(routes / experts) >= mxfp4_mma_per_from`.
* The tier sets per_from to 33 (`sm89.toml:21`). The L4 file overrides it with 4
  (`sm89/nvidia-l4.toml:38` before the fix), a line copied from the L40S file.
* Below that, `matmul_select_mxfp4` (`select_fp4.rs:855`) groups only past `mxfp4_grouped_reuse` = 2
  routes an expert (`select_fp4.rs:907`, kernel `moe_matmul_select_mxfp4_wmma`). Otherwise it runs
  `moe_matmul_select_mxfp4` (`crates/kernels-cuda/kernels/linear/moe/select.cu:434`), one CTA a route
  (`route = blockIdx.x`), each reading `codes + expert·n·k/2` itself.
* At c16, 64 routes touch about 28 of the 32 experts: 64 expert reads against 28, at most 2.3× the
  DRAM bytes before L2 reuse, on a 300 GB/s card.
* Inside `select_mxfp4_mma` (`select_fp4.rs:196-205`), sm_89 takes the run kernel up to
  `mxfp4_run_until` (16 an expert) and the staged kernel past it.

vLLM code: it selects Marlin for MXFP4 on this card once at load (`Using 'MARLIN' Mxfp4 MoE backend`,
`select_mxfp4_moe_backend` at `vllm/model_executor/layers/fused_moe/oracle/mxfp4.py:614`), and
`fused_marlin_moe` (`vllm/model_executor/layers/fused_moe/experts/marlin_moe.py:224`) reads each
expert once a step at every width.

gpt-oss-20b (32 experts, top-4):

| lanes | routes | routes an expert | base | fix |
|---|---|---|---|---|
| 4 | 16 | 1 | under `mxfp4_mma_from`: by-route | same |
| 7–16 | 28–64 | 1–2 | by-route (≤ 2 × 32 routes) | run kernel |
| 17–24 | 68–96 | 3 | grouped wmma (> 2 × 32 routes) | run kernel |

## 6. The fix, line by line

`crates/engine-cuda/profiles/sm89/nvidia-l4.toml`:

```diff
-# MXFP4 experts averaging 4 to 16 routes on the 512-code-run select, past
-# them the staged one (gpt-oss-120b's miniature at c128: 2490 to 2645 tok/s).
-moe.mxfp4_mma_per_from = 4
+# MXFP4 experts averaging up to 16 routes on the 512-code-run select, past
+# them the staged one (gpt-oss-120b's miniature at c128 on an L40S: 2490 to
+# 2645 tok/s); gpt-oss-20b's c8 and c16 decodes (1 and 2 routes an expert)
+# there too, not on the by-route select that reads an expert a route: c16
+# 300 to 490, c8 243 to 278 tok/s.
+moe.mxfp4_mma_per_from = 0
```

* **What `0` does.** It means "any average" (`tuning.rs:274-279`). Since
  `ceil(routes/experts) >= 1`, it behaves the same as 1 (`results/knobs/pie-per0-*` and
  `pie-per1-*` measure the same).
* **Why the line is needed at all.** 0 is also the global default, but the sm89 tier sets 33, so the
  device file has to state it.
* **Which selects it changes.** Only selects of 28 or more routes that average fewer than 4 routes an
  expert:
  * gpt-oss-20b decodes of 7–24 lanes, table in §5. 7–16 lanes come off the by-route select and 17–24
    off the grouped wmma one; both move to the run kernel.
  * a prefill or chunk of 7–24 tokens.
  Decodes of 25 lanes or more, and ordinary prefills, are not touched.
* **The comment.**
  * The run/staged split is unchanged, so the first half stays.
  * The 120b figure was an L40S measurement (#1282, carried into #1320), so it now says so.

## 8. Token equality

Full greedy token-id lists were compared request by request (`scripts/agree.py`, `scripts/tokeq.py`,
on `--dump-all-token-ids` JSONs; `results/tokens-main.txt`).

**Identical between base and fix, in every round with dumped ids** (`verify2` r1–r2, `final`,
`final2`, `xmodel`; round 1 of §3 stored no ids):

* gpt-oss-20b: raw (8 × 256 tokens) and pf8. The shipped commit's engine also matches base on raw
  and c4 (`results/tokens-final2.txt`).
* gptoss-20b-mini: raw and pf8. Its c4 is 8/8 in round 1 and 5/8 in round 2, against 4/8 between
  fix's own rounds.
* MiMo 32-expert miniature: every shape, raw, pf8, c4, c8, c16 and c64, except c16 in one round
  (30/32 identical, the same as its base against base).

**Under concurrency, pie's greedy outputs are not reproducible run to run, even on one engine.**
Which lanes share a step changes the shapes each kernel sees. Here is gpt-oss-20b, base against base
and fix against fix across rounds, then base against fix within a round (`results/verify2`):

| shape | base r1 vs base r2 | fix r1 vs fix r2 | base vs fix, round 1 | base vs fix, round 2 |
|---|---|---|---|---|
| c4 | 6/8 identical, prefix 0.78 | 7/8, 0.89 | 6/8, 0.78 | 7/8, 0.89 |
| c8 | 3/16, 0.49 | 9/16, 0.70 | 2/16, 0.36 | 7/16, 0.59 |
| c16 | 21/32, 0.79 | 3/32, 0.43 | 11/32, 0.60 | 6/32, 0.49 |
| c32 | 28/64, 0.64 | 41/64, 0.76 | 37/64, 0.71 | 30/64, 0.64 |
| c512 | 461/1024, 0.68 | 801/1024, 0.87 | 398/1024, 0.63 | 736/1024, 0.85 |

"prefix" is the mean share of a request's tokens before its first difference.

**Why c8 and c16 diverge, and why that is acceptable.** At c8 and c16 the fix changes the kernel of
every decode step, so outputs diverge as two kernels' accumulation orders would.

* gpt-oss-20b: base against fix gives prefix 0.36–0.60, against 0.43–0.79 for an engine's own reruns.
  The lowest pair, c8 round 1 at 0.36, falls below that range.
* gptoss-20b-mini c8 (2 routes an expert) diverges consistently: 0/16 identical in both rounds,
  prefix 0.46 and 0.50, against 8/16 (0.79 and 0.71) for each engine's own reruns.

These are two correct kernels disagreeing, not one noisy kernel. Why that is acceptable:

1. The run kernel is the one pie already decodes gpt-oss-20b with from c25 to c128, which covers
   every batching cell above c16.
2. `the_routed_selects_answer_the_routed_dot`
   (`crates/kernels-cuda/tests/kernels_cuda/linear/moe_select.rs:199`) checks these kernels against
   the host's routed dot, and passes on both builds (§10):
   * the by-route select at 1–2 routes an expert;
   * the register-dequant kernels at 1, 6, 8 and 12 routes an expert (on sm_89 the run kernel,
     `[8, 1, 4]` and up);
   * the staged kernel at 50.
   No case covers the run kernel at 2–3 routes an expert.
3. Agreement with vLLM's greedy tokens on the same prompts, from vLLM's offline path at the same
   shapes (`results/vllm-tokens`; its streaming client stores no ids), as mean prefix share against
   vLLM (`results/tokens-vs-vllm.txt`, 4 runs each: `verify2` and `final`):

   | shape | base | fix |
   |---|---|---|
   | c8 | 0.30–0.39 | 0.24–0.33 |
   | c16 | 0.41–0.46 | 0.33–0.40 |

   The fix's outputs sit slightly further from vLLM's. With 16–32 requests a run and pie's own reruns
   spreading about ±0.1, this is weak evidence either way. Neither engine's accumulation order is a
   reference for the other's. No logit-level comparison was made: the kernel test in point 2 is the
   numerics check, and it bounds both kernels against the host's routed dot.

## 12. Side findings

1. **Two of the site's L4 cells don't reproduce on this pod.**
   * pie's pbatch at 8fb7e90e6: pf8 4,666 there (TTFT 1,045 ms), 7,325 here (TTFT 661 ms) for the same
     commit.
   * vLLM's batching: 2,193 there (ITL 87.7 ms), 1,765–1,785 here at c512–c1024 (ITL 112–121 ms).
   The other rows agree within about 10%:
   * pie raw: TTFT 129 there, 118 ms here;
   * pie batching at 8fb7e90e6: 1,576 there, 1,436 here at c512, with ITL 63 against 58 ms;
   * vLLM raw;
   * vLLM pbatch.
   The site's vLLM row has TTFT and latency, so it came from vLLM's streaming client, as here (the
   non-streaming path records neither, `vllm_bench.py:318`). What else differed (flags, card) is not
   recoverable from the site.
2. **The site's batching and pbatch cells pick each engine's own best concurrency.** pie's cells were
   pf8 and c512, vLLM's pf64 and c1024. This should be stated on the site.
3. **TTFT and latency are not comparable across engines under concurrency.** pie's client holds the
   queue, while vLLM's engine does. vLLM's TTFT p50 at c4 is 1.75 s because of its queue, not its
   prefill.
4. **pie's harmony rendering of the bench prompt is 545 tokens, HF's is 609.** pie's template omits
   the "You are ChatGPT…/Knowledge cutoff/Current date/Reasoning" system preamble. Without
   `--pretokenized-prompts`, pie prefills 11% fewer tokens than vLLM on the same prompt strings.
5. **pf512 and pf1024 trail vLLM by 23% and 18%.**
   * `max_forward_requests = concurrency` (`pie_bench.py:297-300`) asks for 512 lanes.
   * The working set at 512 lanes leaves room for only 1,024-row fires: "max_forward_tokens 8192 is
     served at 1117" (`serve/load.rs:324-327`), then "1117 and max_forward_requests 512 are served at
     1024 and 512" (`serve/load.rs:589-591`).
   * A prompt-only fire never carries more than ⌊8192/609⌋ = 13 lanes.
   * `engine.prefill_lanes` exists for this case and is not set on the L4. It is untested here.
6. **The L4's `forward_tokens = 2304` does nothing for gpt-oss-20b.** With no `max_forward_tokens`
   stated, sparse-expert or non-recurrent traces take `max(forward_tokens, 8192)`
   (`serve/load.rs:72-79`).
7. **Graph bodies at 512 MiB break arming for gpt-oss-20b** (1 of 1 compositions armed, every shape
   walking eagerly), the same as upstream found on the RTX 4090 (#1417).
8. **The RTX 4090 profile probably has the same c8/c16 gap.** It keeps `moe.mxfp4_mma_per_from = 4`
   (`nvidia-geforce-rtx-4090.toml:41`) on the same sm_89 kernels. Its #1355 raised `mxfp4_run_until`
   to 32, which only moves selects of 17–32 routes an expert. Not measured here.
9. **nsys exports carry the process environment, including API keys** (§13).
10. **vLLM's pf16 is noisy.** Its round 1 read 4,290, against 6,374 and 6,400 in rounds 2–3, while its
    other pf points spread under 1%. It is kept in the mean.

## 13. Playbook notes

* **The site picks each engine's best point of the sweep.** Reconstruct which point from
  `prefill/out` and `out × wall` before profiling anything. Here the pbatch cell was pie pf8 against
  vLLM pf64.
* **Build the measured commit and run it on the pod first.** It separates the site's environment from
  engine changes. Here, the same commit gave 7.3k against the site's 4.7k.
* **Under N = 2C lockstep batching, small differences in seat count become wave quantization.** 215
  seats for 512 requests means three waves. Read `wave avg active pipelines` and the info-level
  admission log (`RUST_LOG=info`).
* **Never commit nsys `.nsys-rep` or `.sqlite`.** They hold the process environment, keys included.
  GitHub push protection caught a RunPod key in one here. Keep traces outside the evidence tree,
  commit text summaries, and run a secret scan before each sync (`scripts/secret_scan.sh`).
* **`--cuda-graph-trace=graph` exports carry graph executions from before `cudaProfilerStart`**
  (negative timestamps, load-time arming). Filter `start >= 0`.
* **No CPU sampling on these containers:** py-spy has no ptrace, and perf_event_paranoid is 4.
* **The L4 is power-capped.** Sample clocks during each run (`nvidia-smi -lms 1000`) and read only
  the at-cap samples.
* **Don't edit a shell script while bash runs it.** Bash reads scripts incrementally. Also, `pgrep -f`
  with a pattern from the current command line matches, and kills, the agent's own shell.
* **vLLM's streaming client stores no token ids.** For a vLLM token reference, run its offline path.
* **A wide catalog of "same kernel family" precedents can mislead.** sm_86 has no run kernel. Check
  what the arch actually dispatches.
